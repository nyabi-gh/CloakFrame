# CloakFrame 종합 분석 보고서

- 분석일: 2026-09-05
- 대상 버전: 1.11.1
- 범위: 소스 구조, 파일 안전성, UI/UX, 영상 처리, 성능, 테스트, CI·배포, 기능 확장
- 분석 방식: 코드 및 설정 검토, macOS 로컬 빌드·테스트·정적 분석
- 제외 범위: 실제 GUI 조작과 화면 렌더링 검증, Windows/Linux 실행 검증, 검출 정확도 벤치마크, 배포된 업데이트의 실행 검증

## 종합 평가

CloakFrame은 핵심 처리와 파일 보호가 잘 구현되어 있으나, 사용자가 결과를 검증하고 문제를 해결하는 경험은 더 보완해야 한다. 기능을 늘리기 전에 검토 결과의 정확성, 문제 파일 식별, 영상 검토 편의성을 개선하는 것이 가장 효과적이다.

원본 보존, 출력 충돌 방지, 모델 무결성 검사, 처리 중 원본 변경 대응, 검토 필요 상태 구분은 중요한 강점이다. 다만 이러한 장치가 검출되지 않은 모든 개인정보까지 제거했다는 보증으로 이어지는 것은 아니다. 제품의 완료 표현과 검토 경험이 실제 보호 범위를 정확하게 전달해야 한다.

이 보고서의 지적 사항은 코드에서 확인한 동작, 그로부터 판단한 위험, 개선 제안을 구분한다. 별도 재현이나 측정이 필요한 사항은 확정된 실행 결함으로 취급하지 않는다. 분석 당시 소스 변경은 하지 않았다.

## 검증 결과와 제한

| 항목 | 결과 |
| --- | --- |
| 새 Debug 빌드 | 성공. `CLOAKFRAME_WARNINGS_AS_ERRORS=ON` |
| CTest | 10개 테스트 대상 모두 통과 |
| clang-format | 추적 중인 C++·Objective-C++ 파일 검사 통과 |
| clang-tidy | 검증 빌드에 포함된 43개 파일 통과 |
| 보조 JavaScript 테스트 | 4개 통과 |
| 번역 검사 | CTest에 포함된 번역 품질 검사 통과 |
| 실제 모델 추론 | 모델 파일·환경변수가 없는 일부 테스트는 내부적으로 건너뜀 |
| 플랫폼 | 이번 실행은 macOS만 확인 |

기존 Debug 빌드는 삭제된 ONNX Runtime 1.28 경로가 캐시에 남아 실패했다. 별도 `out/build/review-audit`에서는 현재 설치된 ONNX Runtime 1.29를 사용해 빌드했다. 기존 Debug 캐시 문제 자체를 수정한 것은 아니다.

검증 빌드는 `CLOAKFRAME_SELF_UPDATE=OFF`로 구성했으므로 실제 업데이터 구현은 빌드·실행 검증 범위에 포함되지 않는다. 업데이트 공통 코드와 관련 테스트의 통과를 플랫폼별 업데이터 전체의 검증으로 해석해서는 안 된다.

macOS 15 대상으로 빌드하면서 macOS 26 대상으로 만들어진 로컬 Homebrew 라이브러리를 연결한다는 링커 경고가 발생했다. 빌드는 성공했지만 이 산출물로 macOS 15 호환성을 보증할 수 없다. 기존 Debug 구성에서는 Sparkle 공개 키 미설정 경고도 확인했다. 이는 로컬 구성에 관한 결과이며 배포본의 키 설정을 확인한 것은 아니다.

주요 검증 명령은 다음과 같다. 실행 환경의 Python 활성화 절차를 적용한 뒤 CTest와 tidy 대상을 실행했다.

```sh
cmake -S . -B out/build/review-audit -G Ninja \
  -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_EXPORT_COMPILE_COMMANDS=ON \
  -DCLOAKFRAME_SELF_UPDATE=OFF \
  -DCLOAKFRAME_WARNINGS_AS_ERRORS=ON
cmake --build out/build/review-audit --parallel 4
ctest --test-dir out/build/review-audit --output-on-failure --parallel 4
cmake --build out/build/review-audit --target cloakframe_tidy --parallel 4
node --test .github/scripts/update-download-badge.test.js
```

포맷 검사는 추적 중인 `*.cpp`, `*.hpp`, `*.mm` 파일에 대해 `clang-format --dry-run --Werror`로 수행했다. 테스트 통과는 실행된 사례에 관한 결과이며 실제 검출 정확도나 모든 플랫폼의 동작을 보증하지 않는다.

## 유지할 강점

- **파일 안전성:** 원본 보존, 출력 경로 사전 충돌 검사, 덮어쓰기 방지, 경로 이탈 방어가 구현되어 있다.
- **원본 변경 대응:** 검토 중 입력이 바뀌는 상황을 고려한 스냅샷과 검사 흐름이 있다.
- **개인정보 보호 기본값:** 저장 전 검토가 기본 활성화되고 이미지 메타데이터 보존은 기본 비활성화다.
- **실패 구분:** 실패·건너뜀·마스킹 없는 출력·미처리 영역을 정상 완료와 구분한다.
- **영상 처리:** 장면 전환, 양방향 추적, 수동 키프레임, 하드웨어 인코더 실패 후 소프트웨어 재시도를 지원한다.
- **공급망 관리:** 모델 해시 검증, 사용자 모델 동의, 업데이트 서명 관련 코드와 테스트가 있다.
- **개발 품질:** 플랫폼별 CI, 포맷·정적 분석, 번역 검사, 파일 안전성과 오류 경로 테스트를 갖추고 있다.

## 우선 개선 사항

우선순위는 실제 보호 범위의 전달, 작업 신뢰성, 사용자 영향도를 기준으로 정했다. 보안 취약점 심각도 등급은 아니다.

### R1. 폴더 접근 권한 문제의 누락 보고 가능성

- 우선순위: 높음
- 판정: 코드상 위험 확인, 권한별 실행 재현 필요
- 근거: [ImageScanner.cpp](../src/ImageScanner.cpp)의 `scanMedia`, [ProcessorWorker.cpp](../src/ProcessorWorker.cpp)의 스캔 결과 처리

폴더 순회에 `skip_permission_denied`를 사용한다. 접근할 수 없는 하위 폴더가 오류로 보고되지 않고 제외되면, 처리기는 그 안의 파일을 전체 수량에도 포함하지 못한다. 읽을 수 있는 파일만 처리하고 정상 완료할 가능성이 있다.

사용자는 폴더 전체가 처리되었다고 이해할 수 있으므로 접근 불가 경로를 명시적으로 집계하고 검토 필요 상태로 연결해야 한다. 현재 테스트 통과만으로 이 경우가 해결되었다고 볼 수 없다.

권장 검증: 읽을 수 있는 이미지와 접근 불가 하위 폴더를 함께 넣고, 누락 경로와 불완전한 스캔 상태가 결과에 표시되는지 확인한다.

### R2. 영상 저신뢰 트랙의 안내와 실제 기본값 불일치

- 우선순위: 높음
- 판정: 코드에서 확인한 불일치
- 근거: [VideoReviewDialog.cpp](../src/VideoReviewDialog.cpp)의 생성자

상단 설명은 저신뢰 트랙이 기본 제외된다고 안내한다. 실제 목록에서는 체크된 상태로 추가하며 툴팁도 기본 포함이라고 설명한다.

보호 여부를 설명하는 문구이므로 실제 동작과 일치시켜야 한다. 현재의 기본 포함 동작을 기준으로 상단 안내와 번역을 수정하고, 체크 상태와 실제 인코딩 대상의 일치를 UI 회귀 테스트로 확인하는 것이 좋다.

### R3. 수동 보정 후 영상 미처리 구간 통계 미갱신

- 우선순위: 높음
- 판정: 코드에서 확인한 갱신 경로 부재, 사용자 시나리오 회귀 검증 필요
- 근거: [VideoProcessor.cpp](../src/VideoProcessor.cpp)의 `processVideo`, [ProcessorWorker.cpp](../src/ProcessorWorker.cpp)의 영상 검토 콜백

`uncoveredFrames`와 `uncoveredSpans`는 검토 전에 계산된다. 이후 수동 트랙을 추가해도 검토 이후 흐름에서 다시 계산하지 않는다. 사용자가 해당 구간을 가려도 이전 경고가 남을 수 있으며, 무엇이 해결되었는지 설명하기 어렵다.

원래 검출·추적이 놓친 구간과 최종 편집 결과에서도 해결되지 않은 구간을 분리해 관리해야 한다. 수동 트랙이 존재한다는 이유만으로 경고를 제거하지 말고 실제 공간·시간상 커버 여부를 판단해야 한다.

권장 검증: 미처리 구간을 완전히 덮는 수동 트랙, 일부만 덮는 트랙, 시간은 같지만 다른 위치에 있는 트랙을 구분해 결과가 갱신되는지 확인한다.

### R4. 결과 요약에서 검토 필요 이유가 충분히 드러나지 않음

- 우선순위: 높음
- 판정: 코드에서 확인한 표시·데이터 구조의 한계
- 근거: [MainWindow.cpp](../src/MainWindow.cpp)의 `onWorkerFinished`, [ProcessorWorker.cpp](../src/ProcessorWorker.cpp)의 결과 집계

완료 대화상자는 전체·마스킹·원본 복사·건너뜀·실패 수를 보여주지만 `uncovered`는 표시하지 않는다. 실패가 없고 모두 마스킹된 것처럼 보이면서 검토 필요 경고가 뜰 수 있다.

내부 `uncovered`에는 검출 영역 수, 영상 프레임 수, 트랙 수가 합산된다. 현재 경고 여부 판정에는 활용할 수 있지만, 이를 하나의 수량으로 확장해 표시하면 의미가 잘못된다.

파일별 결과 모델을 만들고 미처리 영역, 미처리 프레임, 제외 트랙, 스캔 실패, 메타데이터 경고를 구분해야 한다. 각 문제에서 해당 파일이나 시간대로 바로 이동할 수 있어야 한다.

### R5. 파일 추가 시 UI 스레드에서 썸네일 생성

- 우선순위: 중간~높음
- 판정: 동기 처리 확인, 지연 규모는 미측정
- 근거: [MainWindow.cpp](../src/MainWindow.cpp)의 `videoThumbnailIcon`, `addInputPath`

영상 추가마다 FFmpeg를 실행하고 시작·종료를 동기적으로 기다린다. 이미지 썸네일도 같은 추가 경로에서 읽는다. 여러 영상이나 느린 저장장치의 파일을 추가하면 대기 시간이 누적되어 창이 멈춘 것처럼 보일 수 있다.

파일 목록은 즉시 추가하고 제한된 백그라운드 작업으로 썸네일을 채우는 구조가 적합하다. 사용자가 항목을 제거했을 때 결과를 폐기하고, 동시 작업 수와 메모리를 제한해야 한다.

### R6. 원본 세부 정보를 확인하기 어려운 검토 해상도

- 우선순위: 중간~높음
- 판정: 코드에서 확인한 해상도 제한
- 근거: [ProcessorWorker.cpp](../src/ProcessorWorker.cpp)의 `makeReviewPreview`, [VideoReviewTypes.cpp](../src/VideoReviewTypes.cpp)의 `videoPreviewFrameArguments`

이미지 검토용 데이터는 긴 변 최대 1600px, 영상 미리보기는 최대 960px로 축소된다. 이미지 화면의 확대 기능은 이 축소본을 확대한다.

고해상도 단체사진의 작은 얼굴이나 멀리 있는 번호판을 확인하는 데 한계가 있다. 전체 탐색에는 축소본을 사용하되 확대 구역은 원본 해상도로 다시 읽는 방식이 좋다. 영상에도 확대와 원본 해상도 정지 프레임 확인 기능이 필요하다.

### R7. 기본 활성화된 로컬 로그에 파일명 기록

- 우선순위: 중간
- 판정: 코드에서 확인한 동작, 개인정보 보호 UX 개선 제안
- 근거: [main.cpp](../src/main.cpp)의 `setupLogging`, [MainWindow.cpp](../src/MainWindow.cpp)의 `appendLog`, [SettingsDialog.cpp](../src/SettingsDialog.cpp)

파일 로그는 기본 활성화되며 활동 메시지를 그대로 디스크 로그에도 기록한다. 설정에서 끄더라도 다음 실행부터 적용된다.

외부 전송 문제는 아니지만 민감한 파일명이 남을 수 있다. 기본 로그는 경로·파일명을 제거한 진단 정보로 제한하고 상세 로그는 명시적으로 켜도록 하는 편이 좋다. 기존 로그 위치 확인과 삭제 기능도 도움이 된다.

### R8. 모델 다운로드의 명시적 타임아웃 부재

- 우선순위: 중간
- 판정: 코드에서 확인한 설정 부재
- 근거: [ModelDownloader.cpp](../src/ModelDownloader.cpp)의 `downloadModelWithProgress`

모델 다운로드는 이벤트 루프에서 완료를 기다리지만 요청 타임아웃을 설정하지 않는다. 취소 버튼은 있으므로 UI 전체가 막히는 구조는 아니지만 연결이 정체되면 사용자가 직접 취소해야 할 수 있다.

무응답 제한, 전체 다운로드 시간 제한, 재시도를 추가하고 취소·시간 초과·네트워크 오류·무결성 실패를 구분하면 첫 실행 경험이 좋아진다.

## UI/UX 개선

핵심은 입력 → 처리 → 문제 확인 → 수정의 연결을 강화하는 것이다. 아래 평가는 코드 기반이며 실제 화면의 배치·대비·보조기술 동작은 추가 확인이 필요하다.

### 메인 화면과 작업 흐름

현재 모델 설정이 입력보다 먼저 나온다. 일반 사용자에게는 파일을 넣고 얼굴·번호판 중 가릴 대상을 선택하는 것이 먼저다. 모델 파일 경로와 커스텀 ONNX 선택은 고급 설정으로 옮기고, 기본 화면에는 모델 준비 상태와 간단한 속도·정확도 선택을 제공하는 구성을 권한다.

| 영역 | 현재의 한계 | 개선 방향 |
| --- | --- | --- |
| 입력 목록 | 파일 경로와 아이콘 중심 | 파일별 대기·처리 중·검토 필요·실패 상태 표시 |
| 진행 표시 | 단계·진행률·로그 중심 | 현재 파일과 전체 작업 진행을 구분하고 처리 속도 표시 |
| 결과 확인 | 로그에서 문제 파일을 찾아야 함 | 문제 유형 필터, 해당 파일 열기, 실패 항목 재시도 |
| 이미지 검토 | 단축키 설명에 조작법이 집중됨 | 선택·추가·확대 도구를 눈에 보이게 제공 |
| 영상 검토 | 타임라인 스크럽과 박스 편집 중심 | 재생, 프레임 이동, 문제 구간 이동, 확대, 실행 취소 |
| 출력 충돌 | 충돌 시 전체 작업 중단 | 새 작업 폴더 생성·이름 변경 등 명시적 해결 선택지 |
| 작은 화면 | 영상 캔버스와 측면 목록의 최소 폭 합계가 큼 | 접을 수 있는 측면 패널, 가변 레이아웃 |
| 접근성 | 사용자 정의 캔버스의 의미 전달이 제한적 | 검출 영역 목록과 키보드 편집, 상태의 텍스트 표현 |

### 이미지·영상 검토의 일관성

이미지 검토에는 실행 취소·다시 실행, 확대·이동, 마스킹 결과 미리보기가 구현되어 있다. 영상 검토에도 비슷한 수준의 편집 경험을 제공하는 것이 좋다.

특히 영상 화면에는 실제 마스킹 방식이 적용된 결과 미리보기가 필요하다. 현재 영상 검토 요청은 트랙·프레임 정보를 전달하지만 이미지 검토처럼 마스킹 설정을 전달하는 구조는 아니다. 박스의 위치와 최종 결과의 가려짐을 함께 확인할 수 있어야 한다.

검토 필요 상태는 단순한 경고창보다 해결 가능한 작업 목록으로 표현하는 편이 좋다. 사용자가 문제를 확인하고 수정한 뒤 어떤 항목이 해결되었는지도 추적해야 한다.

## 코드 구조와 유지보수성

정적 분석 결과는 양호하지만 책임이 큰 파일에 집중되어 있다. 분석 시점의 주요 파일 크기는 다음과 같다.

| 파일 | 줄 수 | 주요 검토 관점 |
| --- | ---: | --- |
| `src/MainWindow.cpp` | 2,842 | UI 생성, 설정, 다운로드, 업데이트, 모델 캐시, 작업 수명 관리 |
| `src/ImageIo.cpp` | 2,091 | 이미지 입출력과 플랫폼별 파일 안전성 |
| `src/ProcessorWorker.cpp` | 1,579 | 작업 수행, 검토 요청, 결과 집계 |
| `src/VideoIo.cpp` | 1,482 | FFmpeg 연동과 영상 입출력 |
| `src/VideoReviewDialog.cpp` | 1,151 | 영상 검토 UI와 편집 상태 |

줄 수 자체가 결함은 아니다. 대규모 재작성보다 실제 변경이 잦고 테스트하기 어려운 책임부터 분리하는 것이 적절하다.

1. **파일별 결과 데이터:** 문자열 로그와 독립된 결과·경고 구조를 먼저 도입한다.
2. **작업 제어:** 작업 시작·취소·종료와 검토 요청을 UI 생성 코드에서 분리한다.
3. **설정:** 위젯 값과 영속 설정 사이의 변환을 한곳에서 관리한다.
4. **검토 상태:** 박스·트랙 편집을 화면 없이 테스트할 수 있게 분리한다.

추가 설계 개선점은 다음과 같다.

- 얼굴과 번호판이 공통 `FaceDetection` 자료형으로 합쳐지며 유형 정보가 유지되지 않는다. 대상별 색상·통계·마스킹 정책을 제공하려면 검출 종류를 보존해야 한다. 근거: [FaceDetection.hpp](../include/cloakframe/FaceDetection.hpp), [ProcessorWorker.cpp](../src/ProcessorWorker.cpp).
- 추적 설정이 시간보다 프레임 수 중심이다. 예를 들어 30프레임은 24fps에서 1.25초, 60fps에서는 0.5초다. 의도한 허용 시간을 정의하고 FPS로 변환하면 영상별 동작 차이를 줄일 수 있다. 근거: [Tracking.hpp](../include/cloakframe/Tracking.hpp).
- 폴더 스캐너에는 취소 신호를 전달하는 인터페이스가 없다. 대규모 폴더나 느린 마운트에서 스캔 중 취소 응답을 개선할 여지가 있다. 근거: [ImageScanner.hpp](../include/cloakframe/ImageScanner.hpp).
- 영상 검토에서 제한 초과나 잘못된 수동 트랙 데이터를 사용자 취소와 같은 경로로 반환하는 부분이 있다. 내부 검증 실패와 사용자의 취소는 결과에서 구분하는 편이 좋다. 근거: [ProcessorWorker.cpp](../src/ProcessorWorker.cpp)의 영상 검토 콜백.

## 성능과 대용량 처리

현재 영상 처리는 메모리 상한, 디코딩 사전 읽기, 병렬 마스킹을 갖추고 있다. 성능 개선은 측정 없이 처리 구조를 바꾸기보다 사용자 대기와 단계별 병목을 먼저 줄이는 방향이 적합하다.

권장 순서는 다음과 같다.

1. 파일 추가 시 썸네일 생성을 비동기화한다.
2. 이미지 검토를 기다리는 동안 다음 이미지의 검출을 제한적으로 준비한다.
3. 영상 미리보기의 인접 프레임 사전 로딩과 캐시 효율을 측정한다.
4. 디코딩·검출·추적·검토·인코딩 단계별 시간과 최대 메모리를 측정한다.
5. 긴 영상의 데이터 보유 비용이 실제 병목이면 구간별 처리 구조를 검토한다.

영상은 전체 구간의 검출·추적 정보를 보유한다. 메모리 상한은 있지만 긴 영상이 처리 도중 상한에 도달할 수 있다. 구간별 처리를 도입할 때는 경계에서 추적과 마스킹이 끊기지 않도록 검증해야 한다.

검출 프레임을 무조건 줄이는 최적화는 보호 누락에 영향을 줄 수 있다. 정확도 평가 없이 속도 개선으로만 판단해서는 안 된다. 근거: [VideoProcessor.cpp](../src/VideoProcessor.cpp).

## 테스트와 품질 기준

현재 테스트는 경로 보호, 메타데이터, 원본 변경, 추적, 병렬 처리, 서명, FFmpeg 왕복 처리 등 오류 경로에 강점이 있다. 반면 사용자 행동과 실제 검출 품질에는 공백이 있다.

GUI 구현이 테스트 대상에 직접 포함되지 않아 기본값 안내와 동작 불일치 같은 문제를 잡기 어렵다. 우선 추가할 검증은 다음과 같다.

1. 접근 불가 하위 폴더가 있는 배치 작업의 결과 상태.
2. 수동 트랙으로 미처리 구간을 보정한 뒤 통계·경고 갱신.
3. 저신뢰 트랙 체크 상태와 실제 인코딩 대상 일치.
4. 검토 창 종료·취소·작업 종료의 상태 전이.
5. 실제 번호판 양성 이미지와 여러 조건의 얼굴·영상 샘플.
6. 긴 번역문, 작은 창, 높은 화면 배율에서의 UI 배치.

현재 번호판 모델 테스트는 빈 이미지에서 오검출이 없는지 확인하는 성격이다. 얼굴 테스트 역시 실제 모델과 샘플이 제공되어야 양성 검출을 확인한다. 테스트 통과와 작은 얼굴·측면 얼굴·야간 번호판의 충분한 검출은 별개다. 근거: [test_core.cpp](../tests/test_core.cpp)의 모델 테스트, [tests/CMakeLists.txt](../tests/CMakeLists.txt).

모델 테스트를 독립된 테스트 대상으로 분리하면 모델 누락에 따른 건너뜀을 명확히 드러낼 수 있다. 이후 대표 샘플에서 다음 품질 기준을 마련하는 것이 좋다.

- 대상 조건별 검출 누락률.
- 불필요한 마스킹 빈도.
- 영상에서 대상이 가려지지 않은 프레임과 노출 지속 시간.
- 장면 전환·가림·빠른 이동에서의 추적 안정성.
- 처리 시간과 최대 메모리 사용량.

샘플은 개인정보 사용 권한과 재현성을 확보한 자료를 사용해야 하며, 정확도 수치는 실제 측정 후 제시해야 한다.

## 배포와 호환성

macOS 최소 지원 버전은 실행 파일뿐 아니라 번들에 포함된 라이브러리까지 검사해야 한다. 이번 로컬 빌드의 링커 경고는 배포 산출물에 대한 호환성 검증 필요성을 보여주지만 공식 배포본이 같은 문제를 가진다고 확인한 것은 아니다.

Windows/Linux의 태그 릴리스는 업데이트 키를 요구하는 반면 macOS Sparkle 설정은 공개 키와 개인 키가 모두 없는 경우를 허용하고 Apple 코드 서명 검증에 의존한다. 독립적인 업데이트 서명을 필수화할지 정책을 통일할 여지가 있다. 현재 배포본에 키가 없다고 확인한 것은 아니다. 근거: [release.yml](../.github/workflows/release.yml), [CloakFrameSparkle.cmake](../cmake/CloakFrameSparkle.cmake).

권장 보완 사항은 다음과 같다.

- 최소 지원 OS에서 패키지 실행을 검증한다.
- 번들 라이브러리의 최소 OS 요구 버전을 확인한다.
- 플랫폼별 업데이트 서명 요구사항을 명시하고 CI 정책과 일치시킨다.
- 로컬 의존성 갱신 후 오래된 CMake 캐시를 진단하는 절차를 개발 문서에 안내한다.

OCR 기반 이름·전화번호 가리기, 음성 익명화, 사람 전체 가리기도 확장 방향이다. 다만 새 검출 모델과 별도의 품질 평가가 필요하므로 현재 얼굴·번호판 검토 흐름을 완성한 뒤 진행하는 편이 적절하다.

## 개선 진행 기록

### 2026-09-05: 결과 신뢰성 개선

- R1: 폴더별 순회로 접근 실패 경로를 기록하고 다른 폴더의 처리를 계속하도록
  변경했다. 권한 제한 하위 폴더와 디렉터리 심볼릭 링크 순환을 포함한 회귀

  체크 상태와 검토 결과를 확인하는 GUI 테스트를 추가했다.
- R4: 영역·프레임·트랙을 합산하던 결과 필드를 분리하고, 완료 대화상자에
  검출·추적 경고와 메타데이터 경고, 읽지 못한 입력 경로 수를 표시하도록 했다.

  없으므로 수동 박스의 존재만으로 커버 여부를 검증할 수 없다. 경고를 ‘검토 전
  발견한 추적 공백’으로 정확히 설명하도록 바꾸고, 다른 위치에 수동 마스크를
  추가해도 경고가 사라지지 않는 회귀 테스트를 추가했다. 검토 확인 상태와 실제
  커버 검증을 구분하는 후속 설계가 필요하다.

  아직 구현하지 않았다. 이 기록은 전체 개선 계획의 완료를 의미하지 않는다.

  검사를 통과했다. 권한 제한 폴더 회귀 테스트는 이번 환경에서 실제 실행되었다.

### 2026-09-05: 파일별 결과 화면

- 1차 결과 신뢰성 개선과 이 보고서를 `e1cc984`로 커밋했다.
- 파일별 결과를 상태·입력 경로·실제 저장된 출력 경로·상세 메시지로 전달하는
  `FileResult`를 도입했다. 읽지 못한 입력과 사전 출력 충돌도 결과에 포함한다.
- 활동 영역의 **파일별 결과…**에서 전체·확인 필요·실패를 필터링하고, 정렬한
  항목의 상세 원인과 입력·출력 폴더를 확인할 수 있다. 저장에 실패한 경로를
  이번 작업의 출력으로 표시하지 않는다.
- 목록은 마지막 작업에서 보고된 결과만 보유하며 다음 작업 시작 시 초기화한다.
  아직 시작하지 않은 파일은 표시하지 않는다고 안내한다. 사전 충돌 목록은 기존
  충돌 보고 상한을 따른다. 작업 이력 영속화와 재처리 기능은 이번 범위에 없다.
- 병렬 처리 취소 시 실행 중이던 생산자의 결과가 누락될 수 있는 경로를 수정했다.
  이미 시작한 작업의 종료 후 남은 결과를 전달해 파일 목록과 요약에 반영한다.
- 결과 창의 필터·정렬·선택·빈 결과, 스레드 간 결과 전달, 출력 충돌의 미저장
  상태, 취소 중 결과 보존에 대한 회귀 테스트를 추가했다.
- 변경 후 macOS Debug 빌드, CTest 12개 대상, 포맷 검사와 clang-tidy 46개 파일
  검사를 통과했다. 결과 창은 offscreen 환경에서 영어·한국어로 렌더링해 확인했다.
  첫 실행에서 새 테스트가 손상 이미지를 실패로 잘못 예상했으나, 기존의 ‘저장 없이
  건너뜀’ 동작을 확인해 기대값을 수정한 뒤 전체 테스트를 통과했다.
- 모델 부재로 일부 기존 추론 테스트는 건너뛰었다. 로컬 macOS 최소 버전 링커
  경고는 남아 있으며, Windows/Linux 실행 및 자동 업데이트 검증은 포함하지 않았다.

### 2026-09-05: 영상 추적 공백 탐색과 프레임 이동

- 파일별 결과 화면과 취소 중 결과 보존을 `23e666f`로 커밋했다.
- 영상 검토 창에 검토 전 추적 공백을 시작 프레임 순으로 표시한다. 각 항목은
  트랙 번호, 밀리초 단위 상대 시간, 1부터 시작하는 프레임 범위를 보여준다.
  항목을 선택하면 해당 공백의 첫 프레임으로 이동한다.
- 이전·다음 공백 버튼은 현재 프레임보다 앞·뒤에 있는 가장 가까운 시작점으로
  이동한다. 시작점이 같은 공백은 버튼으로 한 번만 방문하며 목록에서는 각각
  선택할 수 있다. 공백을 방문하거나 수동 마스크를 추가해도 기존 경고는 유지한다.
- 이전·다음 프레임 버튼과 좌우 방향키로 한 프레임씩 이동한다. 영상 양 끝에서는
  이동을 제한하고, 박스를 그리던 중 프레임을 바꾸면 진행 중인 드래그를 취소해
  다른 프레임에 잘못 적용되는 것을 방지한다.
- 한국어·영어·일본어·중국어 안내를 갱신했다. 연속 재생, 원본 해상도 확대,
  검토 확인 상태 저장은 이번 구현에 포함하지 않았다.
- macOS Debug 빌드와 CTest 12개 대상, 포맷 검사 및 수정 C++ 파일의 clang-tidy
  검사를 통과했다. 시간 정렬·중복 시작점·이동 경계·키보드 포커스·공백 없는 영상과
  유리수 FPS 시간 표시를 검증했다. 기존 FFmpeg 테스트에서 시작 시간이 0이 아닌
  영상의 미리보기와 순차 디코딩 프레임 일치도 확인했다.
- 한국어 화면은 offscreen 렌더링으로 배치를 확인했다. 이 화면 확인은 실제 영상
  표시 검증을 대신하지 않는다. 모델 부재에 따른 일부 기존 추론 테스트 건너뜀과
  로컬 macOS 최소 버전 링커 경고는 남아 있다. Windows/Linux 실행 및 자동 업데이트는
  이번 검증 범위에 포함하지 않았다.
