# M3 탐지 벤치마크

실행일: 2026-10-20. 장치: Apple M4(배터리 전원), macOS 27.0, 공식 ORT 1.30.0 CPU(시간은 CoreML도). [Rust 포팅 계획](RUST_PORT_PLAN.md) 8장 M3 6단계와 9.2의 소규모 라벨 벤치마크 기록이다. 도구는 `tools/benchmark/`, 자료는 `tests/fixtures/benchmark/`, CI는 `.github/workflows/benchmark.yml`이다.

## 결론

- **1.12.1 대비(9.2 합격선):** 같은 설정(타일 끔, 같은 임계값)에서 새 엔진의 재현율은 1.12.1과 같거나 0.1%p 낮다(얼굴 한 개). 1%p 넘게 떨어지면 안 된다는 기준을 지킨다. 남은 차이는 1.12.1을 Apple silicon의 Homebrew OpenCV로 돌려서 생긴다([아래](#1121-기준의-축소-차이)).
- **YOLO5Face-n 임계값:** 0.3·0.4는 0.5보다 라벨 얼굴 재현율을 0.3–1.0%p만 올리고 진짜 오탐을 2–3배로 늘린다. 기본값은 1.12.1 값 0.5를 유지한다(2026-10-20 결정).
- **타일 모드:** 고해상도 원본(얼굴 사진 203장)에서 라벨 얼굴 재현율이 82.3% → 87.1%(+4.8%p), 라벨 밖 실제 얼굴을 29개 → 53개 찾는다. 대신 진짜 오탐이 7개 → 68개(사진당 0.3개)로 늘고, 시간은 사진당 CPU +0.59초, CoreML +0.46초(원본 세트 평균)다. 늘어난 오탐은 물방울·철망·글자·천 무늬처럼 확대한 타일에서 얼굴처럼 보이는 질감이다. 기본 켬을 유지하고(2026-10-20 결정: 놓친 얼굴이 여분의 가림보다 나쁘고 여분은 검토에서 뺄 수 있음), 타일에서만 나온 감지의 오탐 줄이기는 후속 과제로 이 벤치마크로 잰다. 5단계 기록의 "오탐 0"은 추상 그래픽 배경 사진 13장의 결과였다.
- **번호판:** 1.12.1과 같다(79.7%). 타일 모드는 너비 32 px 미만 번호판을 10% → 33%로 찾는다.
- **CI:** 감지에 영향을 주는 파일이 바뀌는 PR에서 Linux가 S3 세트를 돌려, 1.12.1 기록 결과의 같은 설정 5가지와 기본 설정의 기록 결과에 대해 재현율이 1%p 넘게 떨어지면 실패한다.

## 세트

Open Images V7(2026-10-20 결정)의 검증·시험 분할에서 고정 seed로 뽑았다(`tools/benchmark/pick.py`). 이미지 라이선스는 Open Images가 적은 CC BY 2.0이고 저자·제목·원래 페이지를 manifest에 남긴다. 라벨은 Google의 Open Images 상자(CC BY 4.0)를 너비·높이 비율로 둔다. 이미지는 저장소에 넣지 않고 해시로 받는다(`tools/benchmark/fetch.py`).

- **S3 세트(`manifest.json`, 610장):** Open Images가 S3에 둔 사본(긴 변 1,024 px)이다. 군중(얼굴 상자 8개 이상) 60, 얼굴 240, 번호판 150, 얼굴 없음(사람이 있는 사진 먼저) 100, 번호판 없음(차가 있는 사진 먼저) 60장. 받는 데 몇 분이고 CI가 이 세트를 쓴다.
- **원본 세트(`originals.json`, 203장):** S3 세트의 얼굴 사진 300장 중 Flickr 원본을 받을 수 있었던 것이다(Open Images가 적은 크기·MD5와 같은 파일만). 0.1–21 MP, 중앙값 1.9 MP, 8 MP 이상 46장. 타일 모드를 실제 사진 크기에서 재려고 로컬에서만 쓴다. 33장은 Flickr에서 사라졌고 57장은 아래 요청 제한 때문에 받지 못했다.
- **공통 조건:** 회전 기록이 없고 EXIF 방향이 1이거나 없으며, 성분이 1·3개(CMYK 아님)인 JPEG. 원본이 12 MB 이하인 사진만 후보로 둬서 두 세트가 한 번의 추첨에서 나온다.

**Flickr 요청 제한:** Flickr는 원본을 100–280개쯤 받은 클라이언트에 429를 1시간 넘게 돌려준다(같은 시각 curl은 200, User-Agent와 무관). 처음에는 원본만으로 610장을 만들려 했지만, 제한을 지키며 받으면 한두 시간이 걸리고 CI도 같은 제한에 걸리므로 S3 사본으로 바꿨다(2026-10-20 결정). 받기 스크립트는 429를 받으면 모든 연결이 함께 기다리고, 사라진 원본(404·410)만 건너뛴다. 처음 판은 429를 사라진 이미지로 보고 건너뛰어 세트가 그날의 제한에 따라 달라졌다.

## 평가

`tools/benchmark/evaluate.py`. 종류마다 그 종류의 라벨이 검증된(있음·없음) 사진만 본다.

- **세는 상자:** group-of(여럿을 한 상자로 묶음)와 depiction(그림·조각)은 세지 않는다. S3 세트의 얼굴 865개, 번호판 207개.
- **맞음:** 점수가 높은 감지부터, 같은 종류의 아직 맞지 않은 세는 상자 중 IoU가 가장 높고 0.5 이상인 상자와 짝짓는다. 감지와 라벨의 상자 관례 차이로 IoU 0.4–0.5에 머무는 얼굴은 약 2%다.
- **오탐이 아닌 것:** 짝이 없는 감지라도 같은 종류의 다른 상자 위에 놓이면(IoU 0.5 이상이거나 한쪽의 절반 이상이 다른 쪽 안) 오탐으로 세지 않는다. 한 얼굴에 겹친 두 번째 상자, depiction, group-of 상자 안의 감지가 여기에 든다. 라벨이 빠진 실제 얼굴·번호판 위의 감지도 오탐이 아니고 "라벨 밖 찾음"으로 따로 센다. Open Images 라벨은 배경의 작은 얼굴을 많이 빠뜨려서, 이렇게 하지 않으면 타일 모드가 찾은 실제 얼굴이 오탐으로 잡힌다.
- **재현율**은 맞은 상자 / 세는 상자, **정밀도**는 맞음 / (맞음 + 오탐)이다. 대상이 없다고 검증된 사진(얼굴 101장, 번호판 63장)에서는 사진당 오탐 수도 낸다.
- **계층:** 얼굴 높이(px), 전체 보기에서의 높이(모델 px, 640 / 긴 변 배율), 군중, 가림·잘림(Open Images 속성), 측면·정면(태그), 어두움(얼굴 상자 평균 밝기 BT.601 < 60, 얼굴의 약 10%). 번호판은 너비와 각도(태그).

## 태그

`tools/benchmark/sheets.py`로 만든 crop 시트를 보고 손으로 붙였다(`tags.json`, 상자 번호와 비율 좌표라 두 세트에 함께 쓴다).

- **측면·각도:** 높이 24 px 이상 얼굴은 정면/측면(한쪽 눈이 안 보이거나 거의 옆), 너비 24 px 이상 번호판은 정면/비스듬함으로 나눴다. 너무 어둡거나 작거나 가려져 판단할 수 없는 crop은 `unclear`로 남기고 계층에서 뺐다. S3 세트에서 얼굴 정면 569, 측면 124, 판단 불가 132, 번호판 정면 116, 비스듬함 50, 판단 불가 9.
- **라벨 밖 얼굴·번호판:** 평가한 모든 설정에서 점수 0.3 이상인 짝 없는 감지를 자리마다 하나씩 crop 시트로 보고, 실제 사람 얼굴(작고 흐린 얼굴, 측면, 사진 속 실제 인물 포함, 그림·조각·인형·가면·뒤통수·동물 제외)과 실제 번호판(광고판·배지·스티커 제외)만 `added`로 더했다. 재현율 분모에는 넣지 않는다(라벨 얼굴만으로 1.12.1과 비교하기 위해). S3 세트 얼굴 129개·번호판 9개, 원본 세트 얼굴 118개다.

## 1.12.1 기준의 축소 차이

같은 설정인데 S3 세트의 얼굴 사진 58장에서 두 결과의 상자가 조금 달랐다(IoU 0.93–0.99). 디코드는 OpenCV·djpeg·Pillow가 바이트까지 같았고, OpenCV가 디코드한 PNG를 두 구현에 넣어도 같은 차이가 났으며, 새 엔진을 Homebrew ORT 1.31.0으로 돌려도 결과가 같았다. 원인은 1.12.1 실행기가 쓰는 Homebrew OpenCV 5.0.0(Apple silicon)의 `INTER_LINEAR` 축소다. 이 판은 KleidiCV HAL을 거쳐 x86 OpenCV와 ±1 다르고(766×1024 → 478×640에서 pixel의 52%), 새 엔진은 x86 OpenCV와 바이트까지 같게 옮겼다(M2 3단계, `ort.yml`이 실제 x86에서 확인). 그래서 기록한 1.12.1 결과는 Apple silicon에서 Homebrew로 빌드한 1.12.1의 동작이고, Windows·Linux의 1.12.1은 새 엔진 쪽과 같다. 재현율 차이는 얼굴 한 개 이하라 게이트의 허용 범위 안이다.

## CI

`.github/workflows/benchmark.yml`(Linux, CPU, 감지·사진·벤치마크 파일이 바뀌는 PR과 main push, 수동 실행). S3 세트를 해시로 받아 캐시하고, 기본 설정과 1.12.1을 기록한 5가지 설정을 타일 끔으로 돌린 뒤 `evaluate.py --gate`로 비교한다. 기준은 `legacy/*.json`(1.12.1)과 `engine/default.json`(기본 설정, 이 Mac의 CPU 결과)이다. x86과 arm64의 ORT CPU 결과는 점수가 조금 달라 경계의 감지가 바뀔 수 있지만, 허용 1%p 안이다.

## 재현

```bash
python3 -I tools/benchmark/pick.py <작업 폴더> <출력 폴더> [--originals | --cached-originals]
images=$(python3 -I tools/benchmark/fetch.py ~/.cache/cloakframe-benchmark)
tools/benchmark/run_legacy.sh "$CLOAKFRAME_TEST_ASSETS" "$images" <작업 폴더>
cargo run --release -p cloakframe-engine --example benchmark -- --ort-library "$CLOAKFRAME_ORT_LIBRARY" \
  --models "$CLOAKFRAME_TEST_ASSETS" --manifest tests/fixtures/benchmark/manifest.json --images "$images" \
  --out result.json --gpu off --tiles off --face-score 0.5
python3 -I tools/benchmark/evaluate.py tests/fixtures/benchmark/legacy/*.json result.json
python3 tools/benchmark/sheets.py unmatched "$images" <시트 폴더> result.json
```

원본 세트는 `fetch.py <폴더> tests/fixtures/benchmark/originals.json`과 `--manifest tests/fixtures/benchmark/originals.json`으로 같게 돌린다. 원본은 Flickr 요청 제한 때문에 오래 걸릴 수 있다.
