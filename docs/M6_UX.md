# M6 6단계 계획: 화면 재설계

작성 2026-10-27. [M6 완료 확인](M6_VERIFY.md#ux-문제2026-10-27)에서 메인테이너가 화면이 투박하고 무엇이 무엇인지 구분되지 않아 쓰기 어렵다고 봤다. 버튼 위치 몇 개가 아니라 화면의 뼈대(위계, 단계, 강조가 없음)가 문제라서 전체를 다시 설계한다. 시작점은 `m6-macos-check`(PR #64)다.

## 결정(2026-10-27, 메인테이너)

- **전체 재설계.** 바꾸는 것은 화면 구성과 흐름, 시각 체계, 문구다. engine, 앱 상태와 작업 스레드, 세션·설정·결정 규칙, egui는 그대로 둔다. egui가 걸림돌로 드러나면 그때 따로 묻는다.
- **설계안 먼저.** HTML 설계안(메인테이너만 열 수 있는 artifact, 11개 화면: 밝게 8, 어둡게 3)을 확정했다. 첫 안은 단계 번호, 아이콘 원, 색 배지, 카드가 겹쳐 "AI가 만든 화면" 같다는 평을 받았다. 그래서 단순하고 현대적인 데스크톱 앱 모양으로 다시 그렸다.

## 설계

### 창 구성

창 하나를 세 칸으로 나눈다. macOS 기본 앱과 같은 배치다.

- **도구 막대(높이 52):** 지금 화면의 제목과 부가 정보("새 작업 · 사진 6 · 동영상 2", "처리 중 · 37% · 약 3분 남음"), 오른쪽에 그 화면의 주 동작(추가…, 시작, 모두 취소, 검토하기, 승인하고 저장)을 둔다. 실행 진행률은 막대 아래의 2 px 선이다.
- **사이드바(폭 220):** "새 작업"(실행 중에는 "처리 중", 끝나면 그 실행)과 "검토 대기" 목록. 검토 대기 항목은 폴더 이름, 날짜, 남은 개수다. 지금 메인 화면 맨 위의 "검토를 기다리는 작업" 상자가 여기로 온다. 편집기에서는 사이드바를 접고 도구 막대에 "‹ 폴더 이름"을 둔다.
- **가운데:** 파일 격자, 실행·결과 목록, 검토 큐, 편집기 캔버스.
- **오른쪽 설정 패널(폭 300):** 메인에서는 가릴 대상, 가리는 방법(분할 단추)과 강도, 샘플 미리보기, 저장 전 검토, 저장 위치, 고급 옵션…. 편집기에서는 해결할 문제, 감지·track 목록, 승인 단추.

### 화면

## 구현 단계

단계마다 main에서 브랜치·PR 하나. 기능과 시험의 흐름은 그대로 두고, 시험은 바뀐 이름과 위치만 따라간다.

1. **틀과 메인(`m6-ux-shell`):** `style` 모듈(위 색을 `egui::Visuals` 두 벌로, 간격·모서리·글자 크기, 주·테두리·무테 단추, 분할 단추, 사이드바 항목, 상태 점, painter 아이콘), 창 구성(도구 막대, 사이드바, 가운데, 설정 패널), 메인 두 상태, 고급 옵션 시트(감지 모델 창을 흡수), 테마·언어를 보기 메뉴로, Noto Medium 부분 집합. Tab 순서를 도구 막대 → 사이드바 → 가운데 → 설정 패널로 다시 잡고 `tab_follows_the_screen_from_top_to_bottom`을 고친다.
2. **실행·결과(`m6-ux-run`):** 처리 중·결과 화면, 사이드바의 실행 항목, 진행 선, 항목별 동작.
3. **검토(`m6-ux-review`):** 검토 큐 두 묶음, 사진·영상 편집기의 도구 막대와 오른쪽 패널, 타임라인 모양(놓친 구간 빗금, keyframe 마름모).
4. **확인(`m6-ux-verify`):** 화면마다 `egui_kittest` snapshot(wgpu)을 밝게·어둡게, 세 언어로 찍어 설계안과 비교한다(영어·일본어 문구가 폭 300 패널에서 넘치는지 포함). 글꼴 렌더링이 OS마다 달라 CI의 golden 비교는 하지 않고 이 Mac에서만 본다. 메인테이너가 macOS에서 다시 써 본 뒤 M6 완료 표시와 preview 게시로 넘어간다.

각 단계의 UI 시험은 지금 규칙대로 작업 스레드를 기다린 뒤 정착하게 쓴다. 작업 스레드를 300 ms 늦춘 복사본과 결과를 보내기 직전에 늦춘 복사본, UI가 기다리지 않은 결과를 받으면 panic하는 복사본으로 확인한다.

## 함께 정한 것(2026-10-27, 메인테이너가 추천대로)

- **굵은 글꼴:** egui는 굵기를 합성하지 않으므로 Noto Sans KR·JP Medium을 지금 Regular와 같은 방식(`tools/fonts/subset.sh`, 같은 noto-cjk 태그와 문자 집합)으로 부분 집합해 번들한다. 앱이 약 7.5 MB 커진다. 화면 제목, 사이드바 선택 항목, 주 단추, 묶음 제목, 결과 요약에 쓴다.
- **테마·언어:** 네이티브 메뉴에 보기 > 테마·언어를 더한다(muda, Linux는 egui 메뉴 막대). 창 안에는 두지 않는다. 메뉴가 보내는 `Command`를 시험이 직접 보내 확인한다(muda 메뉴는 `egui_kittest` 밖).

## 1단계 시작 때 정한 것(2026-10-27, 메인테이너가 추천대로)

- **"이미지" 가리기 방법:** 6단계에서 빼고 M6 뒤, stable(M8) 전에 따로 넣는다. core와 사진 파이프라인은 `Method::CustomImage`를 지원하지만 영상 파이프라인, 세션·설정 저장, 앱 화면에는 없고 설계안에도 없다. 그때 영상 경로, 저장, 이미지 고르기를 함께 넣고 설계안으로 먼저 확인받는다. 분할 단추는 채우기·모자이크·블러 세 칸이다.
- **저장 위치 처음 값:** 지금처럼 비워 둔다. 고르기 전에는 시작이 막히고 가운데에 그 이유를 보인다.
- **"추가…" 단추:** "파일…"과 "폴더…"의 작은 메뉴를 연다(rfd는 파일과 폴더를 한 대화상자에서 고르지 못한다). 빈 메인 가운데의 "파일 선택…"은 파일 대화상자를 바로 연다.
- **검토 대기 버리기:** 1단계에서 사이드바 항목의 우클릭 메뉴 "버리기…"(확인을 받음)로 옮기고, 3단계에서 검토 큐 도구 막대의 "이 검토 버리기…"를 더한다.

## 1단계 기록(`m6-ux-shell`)

- **창 구성:** 도구 막대, 사이드바, 가운데, 설정 패널을 egui 패널이 아니라 손으로 나눈 사각형에 차례로 만든다. egui는 위젯을 만든 순서로 Tab을 옮기고 옆 패널은 가운데보다 먼저 만들어야 해서, 패널로는 도구 막대 → 사이드바 → 가운데 → 설정 패널 순서를 지킬 수 없다. 검토 편집기에서는 사이드바를 숨기고, 설정 패널은 메인에서만 보인다.
- **메인:** 빈 상태는 가운데에 놓기 안내와 "파일 선택…" 링크, 파일이 있으면 4:3 썸네일 격자(이름, 영상 길이). 건너뛴 파일과 시작을 막는 이유는 가운데 아래 줄에 한 줄로 모으고, 읽지 못한 경로는 마우스를 올리면 보인다. 영상 길이를 보이려고 썸네일 스레드가 첫 프레임과 함께 길이를 보낸다.
- **사이드바:** 새 작업(실행 중·결과) 항목과 "검토 대기" 목록. 항목은 폴더 이름, 날짜, 파일 수이고 전체 설명은 접근성 이름과 hover로 준다. 클릭으로 검토를 열고 우클릭 "버리기…"로 버린다.
- **고급 옵션 시트:** 가운데 위쪽에 붙는 modal에 감지, 사진, 영상, 감지 모델 네 구획. 감지 모델 창은 없앴고 메뉴의 "감지 모델…"도 이 시트를 연다.
- **보기 메뉴:** macOS·Windows는 muda의 보기 > 테마·언어(체크 항목), Linux는 egui 메뉴 막대. 언어를 바꾸면 네이티브 메뉴를 그 언어로 다시 만든다(Windows는 옛 메뉴를 창에서 떼고 붙인다).
- **확인:** 앱 시험(lib 36, main_screen 15, models_window 2)과 kittest 렌더, 이 Mac의 실제 앱 창을 밝게·어둡게·일본어로 설계안과 비교했다. 작업 스레드 9곳을 시작 때 300 ms 늦춘 복사본, 보내기 직전(14곳) 300 ms 늦춘 복사본, UI frame이 스캔·모델 확인·세션 목록 결과를 기다리지 않고 받으면 panic하는 복사본에서도 모두 통과했다. 네이티브 보기 메뉴는 이 환경에 손쉬운 사용 권한이 없어 눌러 보지 못했고, Linux·Windows 메뉴 코드는 CI가 처음 빌드한다.
- **첫 CI(PR #65):** macOS runner에서 `reviews_kept_by_earlier_runs_are_listed_opened_and_discarded`가 max_steps를 넘었다. 클릭이 검토를 연 frame은 이미 메인 화면으로 배치된 뒤라 검토 큐가 다음 frame에야 썸네일을 요청했고, 시험의 기다림이 빈손으로 지나가 썸네일이 뒤 `run()` 도중 도착했다. 복사본에서 썸네일을 그 `run()` 직전에 간격을 두고 보내 같은 오류를 재현했다. 고친 것: 한 frame 안에서 화면이 바뀌면 `request_discard`로 pass를 다시 해 새 화면이 그 frame에서 그려지고 요청도 나가게 했고(8e7b04c), 시험이 파일 격자 썸네일도 기다리게 했다(0d25400). 결과를 frame에서 받으면 panic하는 복사본에 썸네일을 더해 확인했다.
- **남긴 것:** macOS의 통합 제목 막대(신호등을 도구 막대 안에)는 넣지 않았다. 투명 제목 막대 아래 클릭을 여기서 확인할 수 없어 기본 제목 막대를 둔다. 같은 날 같은 폴더에 저장한 검토 대기는 사이드바에서 구별되지 않는다(설계안은 시각을 보이지만 트리에 현지 시각 crate가 없다).

## 2단계 시작 때 정한 것(2026-10-27, 메인테이너가 추천대로)

- **시각 표시:** `jiff`(MIT/Unlicense)를 들여 결과 제목과 사이드바에 "오늘 14:12"처럼 현지 시각을 보인다. 같은 날 같은 폴더에 저장한 검토 대기도 시각으로 구별된다.
- **끝난 뒤 사이드바:** "새 작업"을 누를 때까지 맨 위 항목은 이번 실행의 결과("끝남")로 남는다. 검토할 것이 있으면 그 검토는 "검토 대기"에 따로 나온다.

- **테마가 한 frame 늦게 바뀌던 것:** 보기 메뉴에서 테마를 고르면 그 pass는 이미 옛 색으로 시작했고 다른 repaint 요청도 없어, 다음 입력이 올 때까지 창 일부가 옛 색으로 남았다. snapshot에서 테마를 바꾼 뒤 첫 그림이 옛 색이라 찾았다. 명령이 그 자리에서 `ctx.set_theme`을 하고 repaint를 요청한다. `the_theme_menu_changes_the_colours`는 마지막 frame이 고른 테마의 창 색으로 그려졌는지 보고, 밝게→어둡게 순서를 넣어 고치기 전에는 실패한다.
- **패널 넘침 시험:** `every_language_fits_the_settings_panel`이 언어마다 설정 패널의 글자를 모아, 글자가 패널 여백 안에 있는지, 단추·라디오·체크 상자·링크 안의 글자가 그 컨트롤 안에 있는지, 글자끼리 겹치지 않는지 본다. 영어 "Mosaic"를 길게 바꾸면 실패한다. 세 언어 모두 넘치지 않았다.
- **고친 것:**
  - 설정 패널: "모양"·"강도" 이름 칸을 두 이름 중 긴 것에 맞춰, 영어 Shape·Strength 줄의 컨트롤이 같은 자리에서 시작한다.
  - 영상 타임라인: 왼쪽 이름 칸이 70 px 고정이라 일본어 "ナンバープレート"가 눈금 위로 넘쳤다. 종류 이름이 더 길면 그만큼 넓힌다.
  - 캔버스 상자(사진·영상): 설계안대로 가리는 상자는 흰 2 px 테두리에 짙은 바탕, 가리지 않는 상자는 흰 점선, 확실하지 않은 후보는 주황 점선과 "확실하지 않음" 꼬리표, 고른 상자는 글자 색 2 px 바깥 선이다. 흰 테두리는 밝은 그림에서도 보이도록 반투명 검은 선을 바깥에 두른다. 설계안의 바탕은 불투명 `#3F3F46`이지만, 미리보기 없이도 가려질 자리를 맞게 잡았는지 보이도록 60 % 투명하게 칠한다. keyframe 사이의 직접 그린 track은 바탕에 점선이다.
  - 체크 상자: 켜진 상자를 글자 색으로 채우고 체크를 반대 색으로 그린다(`style::Check`). egui 체크 상자의 모양을 바꾸는 theme API는 `experimental` 기능 뒤에만 있어 쓰지 않고 직접 그린다. 접근성 역할(CheckBox, 켜짐 상태)은 그대로다.
- **설계안과 다르지만 그대로 둔 것:**
  - 고급 옵션의 민감도는 지금 단계 이름만 보이고 낮음·기본·높음 눈금 글자가 없다. 감지 모델 목록은 라이선스 글 때문에 길어 시트 안에서 스크롤한다.
  - 검토를 켜면 모든 항목이 "검토 필요"로 보류되어, 결과 화면의 사진 행 세부 칸이 비어 있다. 지금 제품 동작이다.
  - 검토 큐의 저장 위치 줄은 전체 경로다. "가린 결과로 보기"는 재생에 적용되고 기본으로 켜져 있다(설계안은 꺼짐).
  - 일본어 결과 세부 문구는 말줄임으로 잘린다.
  - 편집기 도구 막대 왼쪽의 창 단추는 macOS 기본 제목 표시줄에 있다.
  - 넣은 그림에 약한 후보가 없어 확실하지 않은 상자는 그림으로 보지 못했다.
- **확인:** 작업 트리에서 fmt, clippy 두 조합, 전체 시험(568개), cargo-deny 통과. 작업 스레드를 시작 때·보내기 직전 300 ms 늦춘 복사본과 panic 복사본에서 앱 시험 61개 통과(체크 상자 변경 전에 만든 복사본이다. 체크 상자는 작업 스레드를 건드리지 않는다). 체크 상자를 바꾼 뒤 snapshot을 다시 찍어 켜짐·꺼짐·비활성 상자를 밝게·어둡게 봤다.
- **남은 것:**
  - 메인테이너가 실제 앱에서 검토 화면, 타원 미리보기, 이번 단계의 상자·체크 상자를 확인한 뒤 M6 완료 표시와 preview 게시.
  - 처리 중 실패 행의 이유가 비어 있는 것, CLI `--method`, `Models::wait`가 스레드를 join하지 않는 것은 따로 할 일이다.
- **영상 분석 속도(2026-10-28, 메인테이너가 release 앱에서):** 30초 영상 분석이 오래 걸리고 CPU가 놀았다. 1280×720 30 fps 29.5초 클립(884프레임, 감지 0개)을 앱과 같은 설정(YOLO5Face-n, CoreML, 타일 켬)으로 CLI에서 재면 50.3초(실시간의 0.59배)였다. CPU 시간은 59초로 코어 약 1.2개, 타일을 끄면 26.8초였다. 실행 중 GPU 사용률(`ioreg`의 Device Utilization)은 76–84%(실행 전 22%)였다. `sample`에서 추론 스레드는 시간의 78%를 CoreML 예측(`e5rt_execution_stream_execute_sync`) 안에서 보냈다. 병목은 세션 하나가 프레임의 보기(전체와 타일)를 차례로 도는 GPU 추론이고, CPU 일은 이미 전처리 스레드가 미리 한다([M5 기록](M5_VERIFY.md#찾은-것-gpu-1패스의-직렬-전처리)). 같은 설정(타일 끔)에서는 1.12.1보다 빠르므로 9.3 목표 안이다.
  - **CoreML 설정 조사(같은 날, [기록](M6_COREML_SPEED.md)):** Neural Engine은 이득이 없다. 지금의 fp32 MLProgram은 Neural Engine을 고르면 CPU로 떨어지고, fp16 NeuralNetwork 형식은 파이프라인에서 더 느리며 영상 벤치마크 타일 끔 게이트를 넘는다. 원인은 YOLO5Face-n 입력의 batch 차원이 동적이어서 첫 `Reshape`가 CPU에 남고 그래프가 CoreML 조각 두 개로 나뉘는 것이었다. batch를 1로 고정하면 사진·영상 벤치마크 감지가 바이트 단위로 같고, 이 클립의 CLI 실행 중앙값이 57.9초에서 41.7초로 줄었다(같은 부하에서 번갈아 잼). YOLO5Face-n의 CoreML 세션에만 batch를 고정했다(CPU는 점수가 소수 여섯째 자리에서 바뀌어 그대로 둠, 기록의 "구현").
  - **다음에 볼 것:** 해상도에 따라 영상 타일을 켜는 것은 벤치마크와 함께 본다. 노는 CPU에 CPU 세션을 함께 돌리는 것은 실행마다 결과가 달라질 수 있고 D8을 건드린다.
