## 0. 결론 요약

1. **권고: 재작성.** 다만 전부 버리는 게 아니라, *추적·마스킹 알고리즘과 테스트 시나리오는 사양으로 이식하고, 나머지 골격(작업 흐름, UI, 미디어 I/O, 파일 처리, 업데이트)은 새로 설계*하는 방식입니다.
2. 재작성이 리팩터링보다 나은 이유는 세 가지입니다.
   - UX를 바꾸려면 "워커 스레드가 GUI의 모달 창을 동기 호출하고 멈추는" 구조부터 바꿔야 하는데, 이것이 `MainWindow`(3,070줄)와 `ProcessorWorker`(1,898줄)의 뼈대 자체입니다. 고치면 결국 다시 쓰게 됩니다.
   - 미디어 계층(FFmpeg CLI + 원시 프레임 파이프 + 원본 통째 복사 + 2회 디코딩)이 HEIC·HDR·색 관리·성능 개선을 구조적으로 막습니다.
   - 소스와 헤더의 약 5분의 1(약 4,900줄)이 커스텀 모델·파일 게시·잔여물 정리·업데이트 같은 주변부이고, 그중 상당수가 프로젝트 스스로 정한 위협 모델 밖까지 막는 코드입니다. 이 방어 코드가 실제 장애도 냈습니다(1.11.0~1.12.0 macOS 영상 처리 불가).
3. **개별 코드의 품질은 생각보다 좋습니다.** 경고 1건으로 빌드되고, 18개 테스트 실행 파일이 모두 통과하며, RAII·스레드 종료 보장·오버플로 검사가 꼼꼼하고, 한국어·일본어 번역 427문장이 100% 채워져 있습니다. 문제는 한 줄 한 줄의 실력보다 **무엇을 만들고 무엇을 막을지에 대한 설계 판단**에 있습니다.
4. **사용자에게 바로 보이는 결함을 여럿 실측했습니다**: 영상 색 틀어짐, 사진 색 프로파일 소실, 모자이크 블록 크기 설정 무효, 출력 파일 0600 권한, JPEG 출력 용량 급증, Linux에서 모델 다운로드 저장 거부.
5. **제품 관점의 가장 큰 공백**: 아이폰 기본 미디어를 다루지 못합니다(HEIC 사진, 10비트 HDR 영상 모두 거부). 고해상도 사진의 작은 얼굴은 640px 단일 패스라 놓치고, 기본 익명화(12×12 모자이크)는 약합니다.

## 1. 현황

### 1.1 앱이 하는 일

사진(JPG/PNG/BMP/TIFF/WebP)과 영상(MP4/MOV/M4V/WebM, H.264/HEVC/VP8/VP9 8비트 SDR)에서 얼굴·번호판을 찾아 모자이크/블러/채우기/커스텀 이미지로 가린 사본을 출력 폴더에 저장하는 Qt 데스크톱 앱입니다. Windows·macOS(Apple silicon)·Linux AppImage로 배포하고, 영상은 탐지 → 양방향 추적 → (선택) 리뷰 → 인코딩의 2패스로 처리합니다.

### 1.2 구조

```
main.cpp
 └ MainWindow  ─ UI 조립 · 입력 검증 · 모델 해시/복구/다운로드 · 커스텀 모델 승인
                 탐지기 캐시 · 업데이트 3종 · 설정 저장 · 리뷰 창 호스트
     └ QThread ─ ProcessorWorker
          ├ 사진: 원본을 임시 폴더로 복사 → 포맷 판별 → 크기 검사(Qt) → 디코드(OpenCV)
          │       → 탐지 → [리뷰: BlockingQueuedConnection으로 GUI 모달 호출, 워커 정지]
          │       → 마스킹 → 인코드 → (Exiv2 메타데이터) → 원자적 무덮어쓰기 게시
          └ 영상: processVideo()
                  원본 전체 복사 → ffprobe → 1패스(ffmpeg 960px 디코드 → 장면 전환·탐지)
                  → 양방향 추적·후처리 → [리뷰] → 2패스(ffmpeg 풀해상도 디코드
                  → 병렬 마스킹 → ffmpeg 인코드) → 게시

cloakframe_core(정적 라이브러리): 탐지기 4종, 추적, 마스킹, ImageIo, VideoIo,
  모델 다운로드/저장, 잔여물 정리, 업데이트 서명 검증
```

## 2. 잘 된 점 — 재작성해도 지켜야 할 것

- **제품 원칙**: 로컬 전용, 원본 불변, 덮어쓰기 금지, 놓친 구간을 숨기지 않고 프레임 범위로 보고, 메타데이터는 허용 목록 방식. 방향 자체는 옳습니다.
- **추적 후처리**(`Tracking.cpp`): 양방향 IoU 추적 결과 병합, 짧은 끊김 보간(빠른 이동·크기 급변 시에는 양 끝 박스의 합집합으로 덮음), 장면 전환 경계의 짧은 공백 처리, 끊긴 구간을 프레임 범위로 합쳐 보고. 테스트 1,075줄. **이 코드베이스에서 가장 값진 자산**입니다.
- **마스킹 기하**(`Mosaic.cpp`): 타원 마스크가 탐지 박스 모서리를 놓치지 않게 박스를 다시 채움, 소프트 엣지에서도 탐지 박스 안은 100% 덮음, 2px 미만 영역은 단색으로 채움, 커스텀 이미지 아래에 모자이크를 먼저 깔아 투명 영역으로 원본이 비치지 않게 함.
- **탐지기 출력 검증**: 텐서 모양·NaN·박스 범위 검사, 상한 초과 후보를 `omitted`로 보고.
- **엔지니어링 위생**: `-Werror` 가능한 빌드, clang-tidy/clang-format CI, 3개 OS CI, 의존성 버전·해시 고정, 번역 품질 테스트, 위젯 접근성 이름.
- **프라이버시 세부**: Release 빌드 크래시 덤프 차단, FFmpeg `-protocol_whitelist file`, 로그 기본값은 파일명 미기록.

### D1. 영상 출력 색 틀어짐 (실측)

인코더에 BGR24 원시 프레임을 넘기면 FFmpeg가 기본값인 **BT.601 행렬**로 YUV 변환하고, 출력에 색 공간 태그를 붙이지 않습니다([VideoIo.cpp:1141-1223](https://github.com/nyabi-gh/CloakFrame/blob/v1.12.1/src/VideoIo.cpp#L1141)). HD 영상을 태그 없이 받으면 대부분의 재생기·브라우저는 BT.709로 해석하므로 색이 이동합니다.

앱과 똑같은 디코드·인코드 인자로 재현한 결과:

| | 중앙 픽셀 RGB |
| --- | --- |
| BT.709 태그 원본(참값) | (196, 58, 34) |
| 앱 출력을 BT.709로 해석(일반 재생기) | (207, 70, 30) |
| 앱 출력을 BT.601로 해석(FFmpeg 기본) | (195, 59, 34) |

출력의 Y 값이 91 → 100으로 바뀐 것으로 BT.601 행렬이 쓰였음을 확인했습니다. 원본의 색 범위·프라이머리·전달 특성도 모두 사라집니다. 하드웨어 인코더도 같은 경로를 탑니다.

### D2. 사진 ICC 색 프로파일 소실 (코드 확인)

`cv::imencode`는 ICC를 쓰지 않고, 메타데이터 보존 경로도 `dst->clearIccProfile()`을 명시적으로 호출합니다([ImageIo.cpp:2141](https://github.com/nyabi-gh/CloakFrame/blob/v1.12.1/src/ImageIo.cpp#L2141)). 픽셀 값은 원본 색 공간 그대로 저장되므로, Display P3(아이폰)나 Adobe RGB 사진은 sRGB로 해석되어 채도가 빠져 보입니다. ICC는 개인정보가 아니므로 지울 이유가 없습니다.

### D3. 모자이크 블록 크기 설정 무효 (실측)

셀 수를 가로·세로 최대 12개로 묶어 둡니다(`kMaxMosaicCells`, [Mosaic.cpp:53-65](https://github.com/nyabi-gh/CloakFrame/blob/v1.12.1/src/Mosaic.cpp#L53)). 600px 얼굴에서:

| 블록 크기 | 결과 색 수 |
| --- | --- |
| 8 / 14 / 40 | 모두 144(12×12, 결과 동일) |
| 100 | 36(6×6) |

기본 블록 14 기준으로 패딩 포함 168px 이상이면 설정이 아무 영향을 주지 않습니다. UI에는 "Mosaic block size in pixels"로 노출되어 있어 사용자를 오도합니다. 또한 축소에 `INTER_LINEAR`를 써서 큰 영역을 12칸으로 줄일 때 평균이 아니라 표본 몇 개만 반영됩니다.

### D4. 출력 권한 (실측 / 코드 확인)

- POSIX: 임시 파일을 `0600`으로 만들고 그대로 이름만 바꿔 게시하며, 하위 폴더는 `mkdirat(..., 0700)`으로 만듭니다. 검증 결과 출력 파일 `600`, 하위 폴더 `700`([ImageIo.cpp:1104](https://github.com/nyabi-gh/CloakFrame/blob/v1.12.1/src/ImageIo.cpp#L1104), [1311](https://github.com/nyabi-gh/CloakFrame/blob/v1.12.1/src/ImageIo.cpp#L1311)). 영상은 게시 직전에 `fchmod(0600)`을 겁니다([1974](https://github.com/nyabi-gh/CloakFrame/blob/v1.12.1/src/ImageIo.cpp#L1974)).
- Windows: 소유자·관리자·SYSTEM만 가진 **보호 DACL**(`D:P(...)`)로 파일을 만든 뒤 이름을 바꿉니다([ImageIo.cpp:845](https://github.com/nyabi-gh/CloakFrame/blob/v1.12.1/src/ImageIo.cpp#L845)). 같은 볼륨 안의 이름 변경은 보안 설명자를 유지하므로 출력 폴더의 권한을 상속하지 않습니다(확인 필요).
- 결과: 공유 폴더, NAS, 웹 서버 업로드, 다른 계정에서 결과물을 읽지 못하는 상황이 생깁니다. 익명화된 결과물은 "공유하려고 만드는 파일"이라 이 기본값은 목적과 반대입니다.

### D5. Linux 모델 다운로드 저장 거부 (실측, 영향 범위 확인 필요)

`saveModelFile`이 `QDir::mkpath`로 umask대로 폴더를 만든 직후, 그룹 쓰기 비트가 있으면 "공유 폴더"로 판정해 저장을 거부합니다([ModelStore.cpp:299-305](https://github.com/nyabi-gh/CloakFrame/blob/v1.12.1/src/ModelStore.cpp#L299)). umask 002에서 재현했습니다(폴더 `775` → `FolderNotPrivate`). 사용자 전용 그룹(UPG)을 쓰는 배포판에서는 umask 002가 흔하므로 실제 사용자가 첫 실행부터 막힐 수 있습니다. 데스크톱 세션의 실제 umask는 Ubuntu·Fedora 실기에서 확인이 필요합니다.

더 근본적으로, 모델은 로드할 때마다 고정된 SHA-256으로 다시 검증되므로 이 검사는 보안상 얻는 것이 없습니다.

### D6. JPEG 출력 비대 (실측, 합성 이미지)

JPEG을 품질 100 + 4:4:4로, WebP를 품질 101(무손실)로 저장합니다([ImageIo.cpp:2020-2034](https://github.com/nyabi-gh/CloakFrame/blob/v1.12.1/src/ImageIo.cpp#L2020)). 4000×3000 합성 이미지에서 일반 카메라 설정(q90, 4:2:0) 1.1MB 대비 앱 출력 8.3MB(7.3배)였습니다. 실사진은 이보다 덜하겠지만 원본보다 수 배 커지는 것은 확실합니다. 손실 원본을 무손실로 다시 저장해도 화질은 돌아오지 않습니다.

### D7. 모델 중복 로드 (코드 확인)

- 영상이 섞인 실행에서 YOLO5Face·YuNet은 사진용과 영상용 입력 크기가 같은 640인데도 세션을 두 번 만들고 워밍업도 두 번 합니다([ProcessorWorker.cpp:1511-1515](https://github.com/nyabi-gh/CloakFrame/blob/v1.12.1/src/ProcessorWorker.cpp#L1511)). SCRFD(커스텀 전용)만 960으로 다릅니다.
- 입력을 스캔하기 전에 모델부터 로드하므로, 지원 파일이 하나도 없어도 로드 시간을 기다립니다([ProcessorWorker.cpp:539](https://github.com/nyabi-gh/CloakFrame/blob/v1.12.1/src/ProcessorWorker.cpp#L539)).

### D8. 데이터 경쟁 (코드 확인)

병렬 사진 처리 중 `processItem`이 `detector_`·`plateDetector_`(`shared_ptr`)를 락 없이 읽는데([ProcessorWorker.cpp:1221](https://github.com/nyabi-gh/CloakFrame/blob/v1.12.1/src/ProcessorWorker.cpp#L1221), [1228](https://github.com/nyabi-gh/CloakFrame/blob/v1.12.1/src/ProcessorWorker.cpp#L1228)), 다른 스레드는 GPU 실패 시 락을 잡고 같은 객체를 교체합니다([502-519](https://github.com/nyabi-gh/CloakFrame/blob/v1.12.1/src/ProcessorWorker.cpp#L502)). 표준상 미정의 동작이며, 실행 도중 GPU가 실패할 때만 발생합니다.

### D9. 원본 복사 + 메타데이터 보존 (코드 확인)

리뷰에서 "Copy Original"을 고르고 메타데이터 보존이 켜져 있으면 파일을 바이트 그대로 복사합니다([ProcessorWorker.cpp:1319-1323](https://github.com/nyabi-gh/CloakFrame/blob/v1.12.1/src/ProcessorWorker.cpp#L1319)). GPS·시리얼·소유자명이 모두 남습니다. 확인 창에 언급은 있지만 README의 "시리얼 번호와 소유자·작성자 이름은 절대 남기지 않는다"는 문장과 모순입니다.

### D10. 대소문자 무시 비교 (코드 확인)

입력 중복 제거와 "출력 폴더가 입력 안에 있는지" 검사가 파일시스템과 무관하게 대소문자를 무시합니다([MainWindow.cpp:1628](https://github.com/nyabi-gh/CloakFrame/blob/v1.12.1/src/MainWindow.cpp#L1628), [2716](https://github.com/nyabi-gh/CloakFrame/blob/v1.12.1/src/MainWindow.cpp#L2716)). Linux에서 `Photos`와 `photos`를 같은 폴더로 취급합니다. 반면 출력 충돌 검사는 파일시스템을 실제로 조사해서 판단하므로 같은 앱 안에서 기준이 다릅니다.

### D11. omitted 과대 보고 (코드 확인)

YOLO5Face는 NMS 전 후보가 2,000개를 넘으면 초과분을 "안전 상한을 넘어 가리지 못한 영역"으로 셉니다([Yolo5FaceDetector.cpp:319-329](https://github.com/nyabi-gh/CloakFrame/blob/v1.12.1/src/Yolo5FaceDetector.cpp#L319)). 그런데 NMS 전 후보는 대부분 같은 얼굴의 중복 앵커라 실제보다 큰 숫자로 경고합니다. 영상은 점수 임계값 0.1로 탐지하므로 군중 장면에서 나올 수 있습니다.

### D12. 사진 원본 복사본 위치 (코드 확인)

`StageCleanup.hpp`는 "원본 복사본은 시스템 임시 폴더가 아니라 사용자별 디스크 폴더에 둔다"고 적었지만, 사진은 `QDir::tempPath()`에 복사합니다([ProcessorWorker.cpp:1053](https://github.com/nyabi-gh/CloakFrame/blob/v1.12.1/src/ProcessorWorker.cpp#L1053)). 영상만 `privateStageRoot()`를 씁니다. 주석과 코드가 어긋나는 사례입니다.

## 4. 아키텍처 문제

### 4.1 워커가 GUI를 동기 호출

사진·영상 리뷰는 워커 스레드가 `QMetaObject::invokeMethod(..., Qt::BlockingQueuedConnection)`으로 `MainWindow::requestReview`를 부르고, 그 안에서 `QDialog::exec()`가 돕니다([ProcessorWorker.cpp:1254](https://github.com/nyabi-gh/CloakFrame/blob/v1.12.1/src/ProcessorWorker.cpp#L1254), [MainWindow.cpp:3016](https://github.com/nyabi-gh/CloakFrame/blob/v1.12.1/src/MainWindow.cpp#L3016)). 그 결과:

- 사용자가 리뷰하는 동안 다음 파일을 미리 처리할 수 없습니다. 리뷰가 끝나야 다음 파일의 로드·탐지가 시작됩니다.
- 리뷰 모드에서는 병렬 처리가 통째로 꺼지고 전부 직렬입니다. 그리고 **리뷰가 기본값으로 켜져 있습니다.**
- 리뷰 상태를 저장하거나 재개할 수 없고, 테스트하려면 가짜 `QObject` 슬롯을 만들어야 합니다.

### 4.2 거대 클래스

- `MainWindow`: UI 조립, 입력 검증, 모델 해시·복구·다운로드, 커스텀 모델 승인, 실행 상태, 탐지기 캐시, 업데이트 3종, 설정 저장, 리뷰 창 호스트가 한 클래스에 있습니다.
- `ProcessorWorker`: `ProcessingRequest`의 필드 약 30개를 멤버로 하나씩 복사하고, 사진 파이프라인이 450줄짜리 함수 하나이며, 영상 리뷰 결과 변환과 검증까지 맡습니다.
- `ImageIo`: 포맷 판별, TIFF·PNG·WebP 수동 파서, 플랫폼별 원자적 게시, Exiv2 메타데이터가 한 파일입니다.

### 4.3 코어가 Qt와 UI 문구에 묶임

`cloakframe_core`가 `QCoreApplication::translate`로 사용자 문장을 직접 만들고, `QProcess`·`QImageReader`·`QNetworkAccessManager`를 씁니다. 코어만 떼어 CLI나 다른 UI로 쓸 수 없습니다. ROADMAP에 있는 "명령줄 모드"도 이 때문에 어렵습니다.

### 4.4 미디어 I/O = FFmpeg CLI + 파이프

- 원본 전체 복사 → 1패스 디코드 → 2패스 풀해상도 디코드 → 인코드. 디코드·인코드 모두 BGR24 원시 프레임을 파이프로 주고받습니다.
- 4K 60fps면 프레임당 24.9MB × 60 = **초당 약 1.5GB가 파이프를 양방향으로** 지나가고, YUV→BGR→YUV 변환이 두 번 일어납니다.
- 색 태그가 유실됩니다(D1).
- 영상 리뷰 미리보기는 프레임을 옮길 때마다 ffmpeg 프로세스를 새로 띄워 최대 3초 분량을 디코드합니다.
- 리뷰 미리보기(`-copyts` + `select`)와 인코더(`setpts` + `fps`)가 서로 다른 필터 그래프로 같은 프레임 번호를 맞춰야 하는 구조입니다. 테스트로 막고 있지만 FFmpeg 동작에 기대는 취약한 설계입니다.

### 4.5 전역 상태

마스크 캐시(전역 LRU + 계산 중 future 맵), `cv::setNumThreads` 전역 변경, FFmpeg 위치·하드웨어 인코더 가능 여부의 정적 캐시(무효화 없음), 테스트용 전역 setter 다수가 있습니다.

### 4.6 오류 처리 방식이 섞임

예외, `bool`, `QString *error` 출력 인자, `Outcome` 구조체, `Status` 열거형, 그리고 "safety limit" `length_error`(29곳)가 섞여 있어, 같은 실패가 경로마다 다른 방식으로 올라옵니다.

### 4.7 경고 결과물도 출력 폴더에 게시

CONTRIBUTING은 "마스킹이 끝났음을 증명할 수 없으면 fail closed"라 하지만 실제 동작은 "경고와 함께 저장"입니다. 리뷰를 끈 상태에서 0.67초를 넘는 추적 끊김, 강한 탐지가 하나도 없는 트랙, 상한을 넘은 영역은 **가려지지 않은 채 출력 폴더에 저장**되고 상태만 "Review required"가 됩니다. 출력 폴더가 클라우드 동기화 폴더면 그 즉시 업로드됩니다.

## 6. 코드 품질

### 6.1 중복

- `readModelFile` 4벌(탐지기마다), `faceRollFromLandmarks` 3벌, 레터박스 전처리 4벌
- 파일 동일성 캡처 3벌(`VideoProcessor`는 `FileIdentity` 구조체를 통째로 복제한 `VideoSourceSnapshot`을 따로 둠)
- GPU 실패 시 CPU로 다시 로드하는 코드 3벌, Windows `FILE_RENAME_INFO` 조립 2벌

### 6.2 같은 정보의 사본

`ProcessingRequest` → 워커 멤버 약 30개, `ActiveRunState`, `PendingRun`, `DetectorCacheKey`가 같은 설정을 3~4벌 들고 다닙니다. 옵션 하나를 추가할 때 5~6곳을 고쳐야 합니다.

### 6.3 이름과 의미

번호판에도 `FaceDetection`과 `FaceDetections`를 씁니다. 얼굴과 번호판이 점수 임계값 하나를 공유합니다(두 모델의 점수 분포는 다릅니다).

### 6.4 숨은 결합

`MainWindow`가 폴더 항목에 `Qt::UserRole + 10`을 세팅하면, `ThumbnailLoader`가 같은 역할 번호를 "썸네일 이미 요청됨"으로 해석해 폴더를 건너뜁니다([MainWindow.cpp:2726](https://github.com/nyabi-gh/CloakFrame/blob/v1.12.1/src/MainWindow.cpp#L2726), [ThumbnailLoader.cpp:17](https://github.com/nyabi-gh/CloakFrame/blob/v1.12.1/src/ThumbnailLoader.cpp#L17)).

### 6.5 주석

헤더에 이력 서술·변론형 장문 주석("The old path wrote to…", "used to be…", "Three different failures used to be added together…")이 많습니다. 프로젝트 `CLAUDE.md`의 주석 규칙과 어긋납니다. 반면 정작 중요한 규약(프레임 번호 매핑, 좌표계)은 여러 파일에 흩어져 있습니다.

### 6.6 UI 코드

`.ui`나 QML 없이 코드로 위젯을 조립하고, 번역 갱신용 람다(`addRetranslation`)를 위젯마다 등록합니다. `MainWindow.cpp` 3,000줄의 상당 부분이 레이아웃 코드입니다.

### 6.7 비동기 처리

모델 다운로드는 GUI 스레드의 중첩 `QEventLoop`, 확인은 모달 `exec()` 연쇄, 종료는 `processEvents` 폴링입니다. 동작은 하지만 재진입 버그가 생기기 쉬운 형태입니다.

### 6.8 긍정적인 부분

const 정확성, RAII, 예외 경로에서도 스레드를 join하는 처리(`OrderedParallel`의 `StopAndJoin`, `MaskWorkerPool`), 포화 연산을 쓴 크기 계산, 경고 없는 빌드. 기본기는 탄탄합니다.

## 7. 탐지·마스킹 품질 (제품의 핵심)

- **사진은 640px 레터박스 한 번만 봅니다.** 4000×3000 사진은 0.16배로 줄어 60px 얼굴이 약 10px이 되고, nano 모델의 검출 한계에 걸립니다. 단체 사진이나 풍경 속 행인을 놓칩니다(ROADMAP C-4도 인정). → 타일링 또는 다중 스케일이 필요합니다.
- **기본 모델**: YOLO5Face-n(nano). WIDER FACE로 학습해 비상업 전용이고, 개인 GitHub 릴리스에서 내려받습니다(저장소가 사라지면 신규 설치가 막히는 가용성 위험). 대안인 YuNet은 더 약합니다.
- **얼굴만 찾습니다.** 뒤통수, 옆모습, 작은 인물은 얼굴 검출기 특성상 놓칩니다. 익명화 도구는 보통 사람·머리 검출을 보조로 둡니다.
- **번호판**: 512 입력의 end2end 모델이라 NMS 임계값이 무시되고, 얼굴과 같은 점수 임계값을 씁니다.
- **익명화 강도**: 모자이크 12×12 상한(D3). 영상에서는 박스가 움직일 때마다 격자가 새로 잡혀 프레임마다 다른 평균이 나오므로, 여러 프레임을 합치면 정보를 되살릴 여지가 있습니다(ROADMAP A-7). 블러는 σ = 짧은 변/6에 커널이 ±1.5σ로 잘립니다. 기본값이 모자이크입니다. → 기본을 단색 채우기 또는 셀 수 하한이 있고 트랙별로 격자를 고정한 모자이크로 바꾸는 것을 권합니다.
- **영상 추적**: 칼만 필터나 외형 특징 없는 IoU 그리디 매칭이라 빠른 이동과 가림에 약합니다. 0.67초 넘는 끊김은 가리지 않고 보고합니다(4.7).

## 8. 영상 파이프라인과 성능

- **처리 단계**: 원본 복사 → 1패스 디코드·탐지 → 추적 → 2패스 디코드·마스킹·인코드. 탐지는 루프 하나에서 직렬이고, 세션 실행도 mutex로 직렬입니다. 장면 전환 검출도 같은 루프에 있습니다.
- **지원 범위**: 확장자 4종, 코덱 4종, 8비트 SDR만. 아이폰 기본 HDR(10비트 HLG / Dolby Vision)과 MKV·AVI는 거부합니다. 가변 프레임레이트는 `fps` 필터로 고정 프레임레이트로 바꿉니다(프레임 복제·삭제).
- **하드웨어 인코딩**: Linux 후보가 NVENC·QSV뿐이고 VAAPI가 없어, AMD와 최신 Intel 리눅스 사용자는 소프트웨어 인코딩으로 떨어집니다.
- **출력**: yuv420p 8비트 고정, 색 태그 없음(D1).
- **진행률**: 파일 하나를 1단위로 셉니다. 1시간 영상과 사진 1장이 같은 비중이라 진행률 막대가 실제 남은 시간과 맞지 않습니다.
- **좋은 점**: 메모리 예산에 맞춘 배치·프리페치 계획(`videoMaskingPlan`), 하드웨어 인코더가 도중에 실패하면 소프트웨어로 재시도하는 처리는 신중하게 설계됐습니다.

## 9. UI/UX

### 9.1 정보 구조

- 첫 카드가 "모델"입니다(모델 경로 입력란, "SCRFD ONNX 파일 불러오기"). 사용자의 첫 행동인 파일 추가가 두 번째입니다.
- README는 "무엇을, 어떻게 가릴지 고른다"를 2단계로 소개하지만, *어떻게*(모자이크/블러/채우기)는 "고급 옵션" 안에 있습니다. 반대로 NMS 임계값·점수 임계값 같은 개발자용 값은 사용자에게 노출돼 있습니다.
- 영상 품질·코덱·GPU 설정은 별도 설정 창에 있습니다.
- 전체가 스크롤되는 한 페이지이고, 텍스트 로그가 주 피드백입니다.

### 9.2 처리와 완료

- 진행 상태는 상태 표시줄 한 줄과 로그뿐이고, 파일별 상태 목록이 없습니다.
- 경고와 함께 끝나면 14개 카운터가 나열된 모달이 뜹니다. "Tracking gap frames pending user review", "Dropped tracks", "Omitted detection regions" 같은 개발 용어입니다.
- 앱을 켜자마자 업데이트 확인 모달이 뜹니다.

### 9.3 사진 리뷰

- 파일마다 모달이 뜨고, 닫아야 다음 파일의 로드·탐지가 시작됩니다. 1,000장이면 1,000번의 모달과 1,000번의 대기입니다.
- 전체 개요(갤러리), "확인 필요한 것부터" 정렬, 일괄 작업이 없습니다. 미리보기가 최대 1,600px이라 원본 크기로 확대해 볼 수 없습니다.
- 단축키 안내가 한 문단짜리 장문 텍스트입니다.
- "Copy Original"(익명화 없이 저장) 버튼은 공유용 출력 폴더에 원본을 넣는 발목지뢰입니다.

### 9.4 영상 리뷰

- 프레임을 옮길 때마다 ffmpeg를 실행하므로 스크럽이 끊기고, 연속 재생과 마스킹 결과 미리보기가 없습니다.
- 트랙 목록, 갭 목록, 수동 트랙(키프레임/시작/끝/삭제) 버튼이 많아 학습 비용이 큽니다.

### 9.5 결과 창과 재시도

재시도는 출력 폴더 아래 `review-YYYYMMDD-HHMMSS-<UUID>` 새 폴더에 저장합니다. 원래 위치의 경고 결과물은 그대로 남고, 폴더 구조가 깨지며, 이전 리뷰 편집도 사라집니다.

### 9.6 플랫폼 감각

- 모든 OS에서 Fusion 스타일을 강제하고, 글꼴을 하드코딩하며("SF Pro Text" 이름 지정, Segoe UI 10pt), QSS에 px 단위 글꼴 크기를 씁니다. 네이티브 앱이 아니라 웹 페이지 같은 인상이고, 시스템 글꼴 크기 설정을 무시합니다.
- 메뉴 막대 항목과 정보(About) 창이 없습니다. GPLv3가 대화형 프로그램에 요구하는 "적절한 법적 고지"와 모델 라이선스(비상업 조건)를 앱 안에서 볼 곳이 없습니다(ROADMAP F-2, F-3).

### 9.7 지원 포맷 공백 (UX 관점에서 가장 큼)

- HEIC/HEIF(아이폰 기본 사진), 10비트·HDR 영상(아이폰 12 이후 기본 촬영), RAW, MKV·AVI를 지원하지 않습니다. 아이폰 사용자가 기본 설정으로 찍은 사진과 영상은 둘 다 처리할 수 없습니다.
- 처리한 결과물도 색(D1·D2), 용량(D6), 권한(D4) 문제가 있습니다.

### 9.8 접근성과 현지화

접근성 이름과 키보드 조작(박스 추가·이동·크기 조절)에 공을 들였고, 한국어·일본어가 완역돼 있습니다. 재작성 시에도 유지할 수준입니다.

## 11. 테스트

- 18개 실행 파일이 모두 통과합니다. 추적 47개, 코어 70개 함수 등 시나리오가 풍부해서 **재작성할 때 사양서로 쓸 가치가 큽니다.**
- 대부분 자체 `assert`(`-UNDEBUG`)를 쓰고 `main()`에서 테스트 함수를 순서대로 부릅니다. 첫 실패에서 실행 파일 전체가 중단되고, 어떤 테스트가 실패했는지 보고가 없으며, 병렬 실행이나 필터링을 할 수 없습니다. `test_core.cpp`는 3,194줄짜리 단일 파일입니다.
- 모델 테스트는 환경변수가 없으면 건너뛰고 통과로 집계됩니다.
- 탐지 품질 회귀 측정(재현율, 놓친 비율)용 데이터셋이 없어서, 모델이나 전처리를 바꿨을 때 효과를 숫자로 볼 수 없습니다.
- 출력 특성(색, 용량, 권한, ICC) 테스트가 없습니다. 그래서 D1~D6이 테스트를 통과한 채 배포됐습니다.

### 13.3 목표 구조

```
[core 엔진 — UI 의존 없음]
  media/  디코드·인코드(프로세스 내 libav*, HEIF는 libheif), 색 관리(태그·ICC 유지), 메타데이터
  detect/ 모델당 ONNX Runtime 세션 1개, 타일링·다중 스케일, 얼굴 + 번호판(+선택적 사람/머리)
  track/  기존 알고리즘 이식
  mask/   기존 기하 + 트랙별 격자 고정, 강도 하한
  job/    작업 큐, 취소, 진행 이벤트(바이트·프레임 기준), 세션 파일(탐지 결과·편집 저장)

[app 셸]
  상태 저장소 + 화면 흐름(추가 → 설정 → 처리 → 검토 → 내보내기)
  core와는 비동기 명령·이벤트로만 통신(블로킹 호출 없음)

[cli]
  같은 core로 배치 실행
```

핵심 결정 사항:

1. **리뷰는 "처리 후 검토"로.** 탐지는 백그라운드에서 먼저 끝내거나 앞서 나가고, 사용자는 갤러리에서 확인이 필요한 것부터 봅니다. 확인 전 결과물은 출력 폴더가 아니라 세션(앱 내부)에 두고, 승인된 것만 내보냅니다. 4.7의 "경고 결과물 동기화" 문제도 함께 풀립니다.
2. **출력 게시**: 같은 폴더 임시 파일 → fsync → 무덮어쓰기 rename. 권한은 umask와 폴더 상속을 그대로 따릅니다.
3. **색**: 영상은 원본의 colorspace·primaries·transfer·range를 유지하고 태그합니다. 사진은 ICC를 유지합니다.
4. **기본 익명화**: 채우기 또는 셀 하한이 있는 모자이크. UI는 "블록 크기" 대신 "강도"로.
5. **포맷**: HEIC 입력(출력은 JPEG 또는 HEIC 선택), 10비트·HDR 입력은 톤매핑 후 SDR 출력부터 시작.
6. **업데이트**: 플랫폼별 한 가지.
7. **테스트**: 표준 프레임워크, 출력 특성 골든 테스트(색·용량·권한·메타데이터), 라이선스를 확보한 소규모 탐지 품질 벤치마크.
8. **UI**: 첫 화면은 큰 드롭 영역 + 썸네일 그리드, 그다음 "무엇을(얼굴/번호판) · 어떻게(스타일 + 강도, 실제 샘플 미리보기)" 한 줄, 그다음 저장 위치와 시작. 모델 선택은 "정확/빠름" 토글, 임계값은 "민감도" 슬라이더 하나만 고급에. 처리 중에는 파일별 상태 목록, 완료 후에는 평이한 문장 요약("12개 저장, 2개 확인 필요 — 영상 1개에서 얼굴을 1.2초간 놓침")과 바로 검토로 가는 버튼. 네이티브 스타일과 시스템 글꼴, 메뉴, 정보 창(라이선스·모델 조건).

이 보고서를 쓴 뒤 Rust + egui로 결정했고(2026-10-16), 이 보고서의 결론을 반영해 [RUST_PORT_PLAN.md](RUST_PORT_PLAN.md)를 다시 썼습니다. 영상 I/O는 플랜의 판단에 따라 첫 stable까지 FFmpeg 외부 프로세스를 유지하고, 처리량이 부족할 때만 프로세스 내 모듈로 바꿉니다. 이후 결정은 플랜을 기준으로 합니다.

### 13.4 순서

현행 C++ 코드는 결함을 고치지 않고 그대로 두고, 재작성에만 집중하기로 결정했습니다(2026-10-16). 3장의 D1~D12는 현행 코드의 수정 목록이 아니라 새 코드가 되풀이하면 안 되는 항목으로 씁니다.

1. **사양 고정**: 기존 테스트를 언어 중립 시나리오(입력, 기대 출력)로 추출하고, 골든 데이터와 탐지 품질 벤치마크를 만듭니다. D1~D12는 각각 출력 특성 테스트(색 태그, ICC 유지, 블록 크기 반영, 출력 권한, umask 002 저장, 인코딩 파라미터 등)로 만들어 새 코드의 합격 기준에 넣습니다.
2. **core 엔진**: 미디어 I/O → 탐지 → 추적·마스킹 이식 → 작업 큐 순서로 만들고, CLI로 먼저 검증합니다.
3. **새 UI**.
4. **배포·업데이트 단순화 후 전환**: 기존 설정과 모델 캐시를 이전합니다.

## 부록 A. 검증 방법과 결과

### A.1 빌드·테스트

```bash
cmake -S . -B <scratch>/build -G Ninja -DCMAKE_BUILD_TYPE=Debug -DBUILD_TESTING=ON -DCLOAKFRAME_SELF_UPDATE=OFF
cmake --build <scratch>/build --parallel
ctest --test-dir <scratch>/build --output-on-failure --parallel 8
```

결과: 빌드 성공, 18/18 테스트 통과.

### A.2 검증 프로그램 (`libcloakframe_core.a` 링크)

| 항목 | 결과 |
| --- | --- |
| `imwriteUnicodeNoReplaceAtRoot`로 `sub/out.png` 저장 | 파일 `600`, 하위 폴더 `700` |
| 600px 얼굴에 `applyMosaic`, 블록 8/14/40/100 | 색 수 144/144/144/36 |
| 4000×3000 이미지 JPEG: q90 4:2:0 vs 앱 설정 | 1.1MB vs 8.3MB(7.25배, 합성 이미지) |
| `umask(002)` 후 `saveModelFile` | `FolderNotPrivate`, 폴더 `775` |

### A.3 영상 색 재현 (앱과 같은 인자)

1. `color=c=0xC83C28` 1080p 원본을 BT.709로 인코드하고 태그를 붙입니다.
2. `VideoFrameReader`와 같은 인자(`-xerror -protocol_whitelist file -map 0:v:0 -vf setpts=PTS-STARTPTS,fps=fps=30/1:start_time=0 -f rawvideo -pix_fmt bgr24`)로 디코드합니다.
3. `VideoFrameWriter`와 같은 인자(`-f rawvideo -pix_fmt bgr24 … -c:v libx264 -preset medium -crf 18 -pix_fmt yuv420p -map_metadata -1 …`)로 인코드합니다.
4. 출력 태그: color_space/primaries/transfer/range 모두 `unknown`. 중앙 Y 값 91 → 100. RGB는 3장 D1의 표와 같습니다.
