## 1. Unredacted regions are counted but not located

`ProcessorWorker.cpp:1419` reports `omittedDetections + result.uncoveredRegions`
as one number and discards everything else:

```cpp
if (const int uncovered = omittedDetections + result.uncoveredRegions; uncovered > 0)
```

The two summands mean different things:

- `uncoveredRegions` counts **frames**, not objects. `interpolateGaps`
  (`Tracking.cpp:559`) refuses to interpolate when the gap between two
  detections in one track exceeds `maxInterpolationGap` (default 20,
  `Tracking.hpp:92`) and no scene cut spans it, and adds the whole gap to the
  tally. Refusing to guess is correct; losing the location is not.
- `omittedDetections` counts candidates dropped before NMS at the safety cap
  (`Yolo5FaceDetector.cpp:308`, `ScrfdFaceDetector.cpp:619`).

Observed on `faces-tears-of-steel-720p.mov`: 331 regions redacted, 152 reported
unredacted. At 17,620 frames and 24 fps that is 0.86% of frames, roughly 6.3
seconds scattered across the film — not 152 faces. The wording ("detected
region(s) were left unredacted") reads as 152 exposed faces, which is worse than
what happened and gives the user nowhere to look.

Worth doing, in rough order of value:

1. Separate the two counts in the message. They have different remedies.
2. Carry the gap's frame range out of `interpolateGaps` instead of only its
   length, and log the ranges.
3. Mark those ranges on the video review timeline (`VideoReviewDialog`), where
   the user can already draw manual tracks over them.

Nothing here changes what gets redacted, only what the user is told.

## 2. Pass 1 detection dominates video runtime

Measured on the same file (`%LocalAppData%\CloakFrame\logs\cloakframe.log`):

```
Pass 1: decode 2,002 ms, detect+scene 165,760 ms (17,620 frames)
Pass 2: decode 24,656 ms, redact 218 ms, encode-write 12,543 ms, finalize 229 ms
```

Detection is 166 s of a 208 s run — 9.4 ms per frame for YOLO5Face-n at 640 px
on an RTX 5080 via DirectML. The model is tiny; inference itself should be well
under a millisecond, so per-frame overhead is the cost, not GPU maths:

- `VideoProcessor.cpp:566` calls `detect(frame)` for every frame, one image per
  inference, inside the decode loop. No batching, no overlap between decode,
  preprocessing and inference.
- Preprocessing (resize, normalise, HWC→CHW) runs on the CPU per frame.
- The DirectML path forces `DisableMemPattern()` and `ORT_SEQUENTIAL`
  (`OrtAcceleration.cpp:73-75`).

This also explains the low GPU utilisation: thousands of small dispatches leave
the GPU idle between them.

Candidate directions, all of which change behaviour and need a decision before
implementation:

- Detect every Nth frame and let tracking cover the rest. Largest win,
  interacts directly with item 1's gap logic — a stride above
  `maxInterpolationGap` would manufacture uncovered frames.
- Batch several frames into one `Run`.
- Overlap preprocessing and inference with decoding.

**Do not** treat encoding as a problem. Pass 2 spends 24.7 s decoding and 12.5 s
encoding, so NVENC is starved by the upstream, and NVENC is a fixed-function
block that never registers as full GPU utilisation. 44% is expected.

### What measuring changed — 2026-08-09, later

Most of the reasoning above was wrong, and the numbers did not reproduce. On the
same clip and machine the original run took 208 s where a fresh one takes 135 s;
treat the shape of the old figures, not their size.

- **The 2 s decode figure is not the cost of decoding.** It is the time blocked
  in `readFrame`. FFmpeg is a separate process feeding a pipe, so a small number
  means detection kept the pipe full. Pass 2 decodes the same frames in 30 s.
  Decode is already overlapped; the third candidate above is largely already
  true.
- **"Inference should be well under a millisecond" was wrong.** With the input
  already resident on the device a `Run` still costs 1.615 ms. That is the floor
  for this model on this EP, and no input-side change touches it.
- **Batching is not a cheap option.** The model input is `[-1, 3, 640, 640]` but
  the output is `[1, 25200, 16]`, so the batch dimension is fixed on the way
  out. It needs a graph patch or a re-export, not just a larger tensor.

Measured after PR #6, on `faces-tears-of-steel-720p.mov`, 17,620 frames:

```
Pass 1: decode wait 2.3 s, scene cuts 8.6 s, detect 55.5 s
detect: preprocess 14.3 s, inference 38.9 s, postprocess 2.4 s
whole run 110 s
```

Of the 2.178 ms an inference call takes, 0.562 ms (25.8%) is uploading the
4.69 MiB float input. Sending uint8 NHWC and folding the normalise and transpose
into the graph would reclaim about three quarters of that, roughly 7.5 s, plus
most of the remaining preprocessing. `OnnxGraphPatch` already has the machinery.

**The better lever is overlap**, and it changes no arithmetic at all. Scene-cut
detection (8.6 s) and tensor preparation (14.3 s) run serially in front of an
inference call that spends its time waiting on the GPU:

1. Push scene-cut detection to a worker beside `detect()`. Hides 8.6 s, about
   7.8% of the run. The reader reuses one `cv::Mat`, so every submit must be
   waited for before the next `readFrame`, and the worker must be destroyed
   before that buffer is.
2. Overlap preparation of frame N+1 with inference of frame N. Hides a further
   14.3 s, about 21% of the run in total, but needs `Detector` split into
   prepare and infer plus a second frame buffer.

Two things were tried and rejected:

- Reordering `toThumbnail` to shrink before converting to grey. It is *slower*:
  8.6 s becomes 9.9 s. `INTER_AREA` over three channels costs more than a
  dedicated grey conversion followed by a single-channel resize, whatever the
  byte counts suggest. Cut positions and the resulting tracks were unchanged, so
  it was correct — just pointless.
- Frame striding stays rejected on merit, not effort. It changes which regions
  get redacted: a face present for fewer frames than the stride can be missed
  entirely. It belongs behind an explicit opt-in, never as a default.

The extension whitelist alone is not enough: `VideoIo.cpp:662` rejects anything
that is not H.264 or HEVC, so a webm file would have been refused after passing
the extension check. Audio needed no change — Opus and Vorbis are absent from
the MP4-compatible list at `VideoIo.cpp:974` and are re-encoded to AAC already.

`scripts/check_translations.py --strict-source-equality` passes (319 messages in
each language). Nothing else was run: this machine has no MSVC toolchain, so the
build and tests have never executed. Push to CI before trusting it.

Deliberately out of scope: `.mkv`. It uses the same demuxer family and would
likely work, but it was not asked for and is untested.
